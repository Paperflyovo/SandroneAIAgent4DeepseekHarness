## 3. 剩余工作

### 3.1 图片路由测试（**已修复**，2026-09-30）

`tests/deepseek-image-routing.test.mjs` → `renamed DeepSeek vision route uploads and sends durable images through the real LLM runtime` 现在通过。这是 0.1.5 → 0.2.0 的**契约漂移**，fixture 一个都没跟上，共四处：

1. **`resolveApiKey` → `resolveAuth`**：0.2.0 的 `DeepSeekAdapterOptions` 换掉了旧钩子，`resolveAuth(connection)` 返回 `{ headers, onRequestError? }`。旧钩子**永远不会被调用**，`request()` 直接 `TypeError: this.dependencies.resolveAuth is not a function`，被 `generate()` 包装成 `TRANSPORT`，所以现象一直只是「DeepSeek Messages transport failed」，看起来像网络问题。
2. **Files API 响应体形状**：0.2.0 的 `parseFileObject` 严格校验 `type: "file"` / `mime_type` / `size_bytes` / `created_at`（ISO-8601 字符串）。0.1.5 的 `object` / `bytes` / epoch 秒 `created_at` 被判 `INVALID_RESPONSE`；该错误在 `RequestFiles.resolve` 里被包成 `FileResolutionFailure`，于是**每次请求都静默回退到 inline base64**——上传照发，但请求里不带 file id。
3. **Messages 流缺 `message_delta`**：`stop_reason` 由 `message_delta` 事件结算，只有 `message_stop` 会被判 `MALFORMED_RESPONSE`。
4. **file id 的表示位置**：0.2.0 是 `{ type: 'image', source: { type: 'file', file_id } }`；0.1.5 是顶层 `{ type: 'file', file_id }`。

另外 `resolveFiles` 现在是**必需语义**：0.2.0 在未提供时每个请求都 `new DeepSeekFileStore()`，而复用索引住在 store 上，所以同一张图会逐请求重复上传。真实 provider 注入的是进程级 store。fixture 已照做，并把索引路径改到 `tmpdir()`——默认路径是用户真实的 `DSH_HOME/llm-deepseek/files-v3.json`，既会把 fixture 记录写进用户数据，又会让测试复用到上一次运行的 id 而不是重新上传。

**排查手法（下次直接用）**：`failure` 对象在跨到 `finish` chunk 时已经脱掉 `cause`，所以在测试里打印 `chunks.at(-1).reason.failure` 拿不到东西。要么直接调 `adapter.generate(...)` 自己 `for await` 捕获原始异常，要么包一层 `DeepSeekFileStore` / `DeepSeekUploadIndex` 的方法打日志。本次两者都用了，才定位到第 2 条。

## 4. 这个环境里的坑（每条都真实踩过，代价很高）

1. **不要用 `[System.IO.File]` + 相对路径。** 它用 .NET 的工作目录，`Set-Location` 不会改它。我因此在仓库根建过 3 个空文件（`package.json`、`pnpm-workspace.yaml`、`.pnpmfile.cjs`）。**一律用绝对路径。**
2. **绝不要让 PowerShell 写补丁。** `Out-File` 会写成 CRLF + BOM，补丁直接失效。**用 `git diff ... --output=<file>`**，git 自己落字节。
3. **不要在这个仓库里 `Get-ChildItem -Recurse`。** `sandrone-harness/runtime/tmp/` 下有数百个 QA 残留目录和断掉的符号链接，会刷屏并跑飞。**用 grep 工具**（ripgrep 自动忽略）。
4. **pnpm 的补丁应用比 git 严格。** 零上下文（`-U0`）补丁能通过 `git apply --unidiff-zero`，却会被 pnpm 以 `ERR_PNPM_PATCH_FAILED` 拒绝。生成补丁一律 `-U3`。已有守卫测试拦这条。
5. **pnpm 状态会卡死。** 目录被删/替换失败后，`pnpm install` 和 `--force` 都会说 "Already up to date" 而不修复；删 `node_modules/.modules.yaml` 也没用。**唯一有效的是 `pnpm add -D <pkg> -w`**（做一次真实的依赖变更，强制重链）。
6. **Electron 二进制需要镜像。** 它从 GitHub Releases 下载，这个网络会 `TypeError: fetch failed`。`.npmrc` 里已固定 `electron_mirror=https://npmmirror.com/mirrors/electron/`——**这条对全新 clone 和 CI 是必需的**。
7. **`pnpm run <script>` 会在依赖过期时自动 install。** 想单纯跑校验脚本，用 `node scripts/<x>.mjs`。
8. **提交前跑 `git status` 垃圾检查**（`node_modules/`、`release/`、`runtime/`、`tmp/`、`space/`、二进制、日志）。
9. **改动依赖树 / 原生插件 / Electron 版本后，先跑真实启动再报告。** 这次 141/142 测试全绿而应用一行代码没跑起来过。

## 6. Sandrone 侧已建立的机制

- **`patches/manifest.json`**：每个补丁的存在理由（`reason`）与**删除条件**（`removeWhen`），外加 `preferenceBudget` 棘轮。
- **`pnpm run verify:patches`**：强制清单 ↔ `pnpm-workspace.yaml` ↔ `patches/` 三者一致；`lastVerified` 必须等于当前锁定版本（升版时强制逐个确认或删除）；偏好类补丁不得超预算；并校验**全部 6 处版本钉**（`.pnpmfile.cjs`、`verify-upstream.mjs`、`upgrade-backup.cjs`、`package.json`、workspace 键、补丁文件名）。
- **`pnpm run canary [--version X]`**：不碰 lockfile、不装依赖，预测哪些补丁会在目标版本冲突，并指出**哪个冲突直接删比修更便宜**。
- **`docs/upstream-parity-review.md`**：与官方 0.2.0-rc.2 的逐维对比、已更正的错误判断、§8.0 有实测的升级起点表。
